# 第四步：提取、校验和两层查重

日期：2026-10-06。当前实现决策；替代旧文档中“process 返回 501、OCR 待实现”的描述。

## 实际链路与模型选择

上传 → 保存原件/来源登记 → 接收结果分支 → POST process → 原生文本或本地 OCR → OpenAI 结构化提取 → 原文证据核对 → 确定性校验 → 业务重复候选 → 返回处理结果。

采用 Poppler + Tesseract（eng/deu），不依赖云 OCR 凭据。按页判断文本质量；含图片或文本质量不足的页转 OCR，混合 PDF 可以同时包含两种路径。含 logo 的文本页也会保守转 OCR，这是当前启发式的限制。保存页文本、读取方式、OCR 词坐标及置信度。OCR 置信度不能等同字段准确率。

用户授权使用 OpenAI 并验证本地密钥。使用 gpt-4.1-mini 作为本轮成本与实现复杂度适中的基线，真实请求已验证可用，不宣称它是所有模型中的最佳选择。采用 Chat Completions 的严格 JSON Schema；未引入没有必要的 LangChain/LangGraph 层。参考 [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 和 [模型说明](https://developers.openai.com/api/docs/models/gpt-4.1-mini)。Gemini/Grok 仅保留用户本地备用凭据，未接入或测试。

密钥写入被 Git 忽略的 .env，由 Compose 仅传给 Python。三个用户密钥文本文件均已加入忽略规则，未写入工作流、镜像或日志。修改 .env 后运行 docker compose up -d python-api 才会更新容器配置。/health 的 extraction 标志仅说明配置存在，不能证明服务可用。

## 提取与校验边界

保存模型提取初稿、字段证据、标准化字段和异常，模型不得计算、修补金额或推断缺失字段。证据必须来自指定页；并排栏地址允许逐原始分行核对，不允许拆散单行任意拼词。证据能验证文字存在，不能证明模型的语义归类正确。

金额用 Decimal。币种精度与容差显式配置；日期不明确、裸 $、缺失字段、负金额均提示审核。可明确判断无调整项时检查净额+税额=总额；折扣、运费、多税率结构仍需人工确认，不使用简单行合计误判。C 的 129.00 保留，差额 10.00 由代码指出。

本轮只提取表头和汇总金额，没有实现行项目/多税率完整计算。所有处理完成的发票都仍需要人工审核；HTTP 200 是处理完成，不是审核通过。技术失败保存 failed attempt 并返回 502/503，不创建假审核任务。

## 两层查重与处理重试

1. 来源四元组保持原契约；相同来源/内容返回同一 receipt；相同来源不同内容返回 409。新来源同字节保留新 receipt，复用 invoice_id。
2. 提取后，以供应商税号或规范化的供应商名称+地址，加发票号识别候选。发票号比较忽略空格，金额和币种作为候选佐证。名称相似不单独证明重复。不同字节保留独立发票，不自动合并/删除；缺少关键字段返回 not_evaluable。

GET 动态计算候选，因此后进入的重复件也会反映在旧件上。仅比较各发票最新成功状态，避免历史提取版本重复计数。

同一 pipeline_version 已处理时直接返回，避免重试反复调用模型。处理版本更新后下次 POST 创建新 attempt，保留旧初稿；失败重试可复用已读取的页文本。当前 pipeline 为 step4-v5。单 worker 是明确部署约束；启动时将中断的 processing 标记 failed。

- 原模板和 v1 均保留。新增 n8n_workflows/01_AP_intake_process_v2.json，JSON 可解析、连接检查完成，已导入并发布到本地 n8n，实例 ID APIntakeProcessV2；导出文件 active=false。

- step_04_verification.json 保留未配置模型时的真实 OCR/混合页和失败分支结果，不能把这些 503 当作提取完成。
- step_04_field_evaluation_v2.json 保留早期证据引用失败的评估；step_04_field_evaluation.json 是最终版本字段评估。
- step_04_n8n_verification.json 是真实表单执行结果：文本、OCR、错误金额、重复重试及来源冲突。
- 40 个本地测试通过；模型桩测试只验证应用行为，真实字段效果以独立 HTTP 评估为准。存在一项 Starlette TestClient 依赖弃用警告，无测试失败。

首轮 16 个文件不是 16 个独立模板：5 个文本样本，11 个图像 PDF 中 5 个是这些样本的栅格版本，6 个来自 FATURA。expected_fields.json 已记录人工查看后的来源与可见字段，后端不读取答案。评估含空值及重复业务样本，不能宣传为泛化准确率。

## 最终字段结果

16/16 文件处理完成，123/128 个比较字段严格匹配（包含空值与重复样本）。5 份文本样本预期字段全部匹配；所有预期异常代码均出现。OCR 4/5/6 的发票号存在额外空格，保留原始提取值，查重比较时忽略空格。OCR 11 的供应商名及净额未可靠识别，字段为 null 并进入人工复核。其余字段匹配不代表所有未纳入断言的字段已正确；本轮不是独立泛化基准。

真实 n8n 文本/OCR/金额异常、同 ID 重试及冲突路径通过。后端重启后原件哈希一致、处理结果保留；重复 process 返回同一 attempt。首轮数据已经进入本地数据库，后续再次上传常会看到重复候选，这属于预期，不应删除记录来伪造首次上传演示。
