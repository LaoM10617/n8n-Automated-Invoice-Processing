## Business flow

Upload one invoice or fetch a selected email batch. Archive, extract and validate every attachment; save automatic decisions, review tasks or processing failures. Only after all attachments finish, freeze the intake run membership and read current database decisions.

If reviews remain, send one local pending reminder, then wait and re-read the same batch every **70 seconds**. Reviewers use the existing portal to compare the original, save edits, and approve or reject. The Wait node never approves an invoice. Once all decisions are final, send one batch summary with new/reused records, approved/rejected counts, failures, skips and the export portal link.

Approved records are already available in the export register, even while another invoice waits. Users select records and generate Excel when needed. No file is generated by the batch summary. Rejected and pending invoices remain excluded. Approval and export are not payment.

This removes per-invoice notification steps from the native intake route. Existing lower review-event and Excel-event entries stay for legacy/recovery and selected Excel export notifications. No new infrastructure, model feature or Phase03 work was added.

## Minimal implementation

- `backend/intake_batches.py`: fixed batch membership, current review counts, and persisted pending/summary notice claims. Two small tables use the existing SQLite database.
- `backend/intake_stages.py`: optional `notification_mode` defaults to legacy invoice mode; native intake uses batch mode. Persist whether a run created a new invoice.
- `backend/outcomes.py`: batch-mode decisions remain saved but bypass individual review notices; summary delivery records their completion.
- `backend/app.py`: register the batch routes.
- Protected POST `/api/ap/intake-batches`, GET `/api/ap/intake-batches/{batch_id}`, protected POST `/api/ap/intake-batches/{batch_id}/notify/{phase}`.
- Workflow: batch-mode source metadata, saved-decision/review nodes, batch status, pending branch, Wait/recheck loop and summary. The upload response is returned before human waiting. `Read Batch Status` executes once over completed items.
- Removed the old 1,200-second workflow timeout. Individual HTTP timeouts remain. Installed n8n 2.42.3 persists time waits from 65 seconds; 70 seconds avoids short waits remaining only in process memory.
- `scripts/build_batch_wait_workflow.py` and candidate/operations files describe the change from the saved original. They are construction artifacts; use the published export to reproduce the delivered instance.

## Operation and recovery

Use the existing upload form and email trigger. Open local Mailpit for pending links or the final summary. After submitting the last manual decision, allow up to one polling interval plus request time. An approved row is immediately available in the export portal; the summary can arrive later.

Processing failures and skipped attachments appear separately from rejected invoices. Unresolved review state keeps the batch waiting for investigation. The wait has no automatic approval deadline. To abandon a demo batch, explicitly stop its waiting execution; stopping n8n does not cancel it.

Notice claims prevent repeated or uncertain SMTP sends. If a notice is failed or remains in sending/unknown state, the route stops with an error instead of automatically resending. Inspect the saved notice and Mailpit before any operator repair. This change does not add an automatic recovery job or a notice reset endpoint.

For rollback, stop new intake and resolve or explicitly stop batch-wait executions first. Restore the before-change workflow/version, or follow the Stage A receiver-switch instructions in `AP_native_agent_demo_operations.md`. Preserve the added tables and audit records. Existing batch-mode invoices retain that mode, so inspect outstanding batches when switching; a workflow switch alone does not send their summaries. Do not run the same email batch through two versions.
