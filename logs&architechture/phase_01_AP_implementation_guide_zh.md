# 第一阶段：AP 接收处理实施指南

更新日期：2026-10-06

本文是实施计划，不是完成报告。用户明确要求本指南使用中文；后续代码注释、n8n 节点说明和演示界面仍使用英语。

2026-10-06 当前修订：第一轮同时使用 `test_data/first_round/text_pdf`（5 份）和 `ocr`（11 份无文本层 PDF）。接收支持 PDF/JPEG/PNG；真实 OCR 是第一阶段必要验收项，不能仅以文本 PDF 主线通过结束阶段。最小接收后端已开始实现，最新契约见 `decision_2026-10-06_intake_ocr.md`，实际进度见 `handoff.md`。下文旧的拟议接口若有差异，以该决策及应用 OpenAPI 为准。

## 1. 阶段目标与完成条件

先实现单张样板发票的真实链路：

> 上传 PDF → 保存原件和接收记录 → 提取与校验 → 重复识别 → 保存待审核任务 → 打开审核页面 → 接收到审核链接通知。

随后接入邮件入口，让邮件附件与上传文件共用处理链路。先用少量样本验证，再做批量测试。

第一阶段结束时，应能根据 invoice_id 找到原件、来源、提取初稿、校验结果和待审核任务；重跑相同输入不应创建重复任务。审核页面本阶段至少真实展示原件和字段。修改、批准、拒绝的写入闭环属于后续审核阶段；未实现时不显示可操作的假按钮。

本阶段不实现自动批准、真实记账导出、实际付款、AP/AR 到期调度或完整 MCP 查询。02 的审核事件和 03 的数据查询只约定边界。

## 2. 当前事实与模板问题

已检查根目录 AGENTS.md、workflow_map.md、Architechture_rough_summary.txt、AP_workflow.md、compose.yaml 及原始模板。

- 原始文件：`n8n_workflows/Email invoice archiving & data extraction.json`。保留不动。
- JSON 可解析，含 17 个功能节点、9 个说明节点，active=false。
- `Check: Message already processed` 无后续连接；`If` 参数为空且未接线。当前入口无法到达提取链路。
- 附件过滤仅检查 binary 存在；上传只取第一个附件，没有逐附件拆分。
- Sheets 查询 uniqueKey，但保存节点没有写入该键，查重登记不闭环。
- 提示词包含特定商品代码及 CGST/SGST，并要求不断补提取直到金额相等；不能直接用于本项目。
- 下载后分出提取与 SFTP/删除链路；删除邮件与 Drive 文件未受完整业务成功条件控制。
- 模板没有审核任务、审核页面或审核通知。
- 当前 Compose 仅配置 n8n 2.42.3；仓库检查未发现 Python 后端实现。
- 尚未验证目标实例导入、凭据绑定或真实执行。模板元数据不构成本地凭据可用的证据。

现有 AP_workflow.md 保留了历史讨论。执行时以根目录 AGENTS.md、workflow_map.md 与本文的第一阶段范围为准：01 通知后结束，不用 Wait 等待审批，也不直接调用 02。

## 3. 总体实施顺序

1. 使用已筛选的 5 份文本 PDF 和 11 份 OCR PDF，补齐 OCR 样本的来源映射与预期字段，确认统一输入结构。
2. 定义最小接口，开始 Python 的真实保存与接收登记。
3. 建立 n8n 上传入口，验证二进制文件确实保存。
4. 在同一处理接口实现原生文本与 OCR 路径，至少各验证一份真实样本，再接结构化提取、确定性校验与业务重复识别。
5. 创建真实待审核任务和最小可打开页面。
6. 将审核通知发送到测试收件端，完成单张上传 happy path。
7. 接入 Gmail，先测单封，再测多附件。
8. 扩大 OCR 布局、缺失和错误场景；第 4 步已要求真实 OCR，不推迟到邮件联调后才开始。
9. 最后做批量处理与故障恢复验证，更新交接记录。

可在第 2 步前后单独做 1～2 封邮件的凭据/附件冒烟测试，但邮件批量测试不应阻塞后端开发。

## 4. 第一步：准备测试材料

### 4.1 样本选择

起步选 3 张字段清晰的文本 PDF，至少包含供应商、发票号、日期、币种和总额；优先含到期日、净额、税额的样本。第一张成功后增加不同布局与多页样本。

可用来源（此前查阅项目说明，尚未下载或逐张核验）：

- [invoice-agent dataset](https://github.com/superintelligenceco/invoice-agent/tree/main/dataset)：50 张合成 PDF、5 种布局与标准答案，可仅复用数据。取用时记录来源版本和许可；不要照搬它的批准/拒绝标签作为本项目规则。
- [synthetic-invoice-gen](https://github.com/alamgirqazi/synthetic-invoice-gen)：后期按需批量生成 PDF；先核实运行依赖和许可。
- [FATURA](https://arxiv.org/abs/2311.11856)：面向 OCR 的发票图像数据集；不是文本 PDF 集合，放到后期。

建议后续创建 `demo_data/invoices/` 和 `demo_data/expected/`，但本次仅创建文档，不创建这些目录或样本。

### 4.2 预期结果

为每个样本人工确认 case_id、文件名、供应商、发票号、开票日、到期日、币种、净额、税额、总额和预期异常。未印在原件上的字段记为缺失，不制造答案。

正常样本和故意异常样本分开标记。生成式样本应保存生成数据作为标准答案；不能用同一个提取器的输出充当答案。

验收：可以人工对照原件核对字段；样本不含真实个人或业务敏感信息。

## 5. 第二步：确定最小接口并开始后端

### 5.1 建议实现方式

第一版建议一个 Python HTTP 应用（例如 FastAPI）、SQLite 和持久化原件目录。属于待落实的技术选择，并非当前实现。不要先拆微服务、增加队列或建立复杂任务平台。

先写文件保存和数据库登记，再逐段加入提取、校验与审核任务。业务状态由后端持有，n8n 只根据响应分流。

### 5.2 拟议接口契约

以下路径是建议，全部待实现；实现前固定字段并同步实际响应，不把表格视为已有 API。

| 接口 | 输入/用途 | 关键输出 |
| --- | --- | --- |
| `GET /health` | 服务连通性 | 服务状态，不代表整个流程可用 |
| `POST /api/ap/intakes` | multipart 文件、来源、来源消息/上传 ID、附件 ID | receipt_id、invoice_id、delivery_duplicate、original_ref |
| `POST /api/ap/invoices/{invoice_id}/process` | 处理已保存原件 | processing_status、validation_issues、business_duplicate_status |
| `POST /api/ap/invoices/{invoice_id}/review-task` | 幂等创建待审核任务 | review_task_id、invoice_id、direction、review_status、review_url |
| `GET /api/ap/invoices/{invoice_id}` | 获取当前记录 | 字段、异常、状态、原件引用 |
| `GET /review/{invoice_id}` | 浏览器访问 | 原件与字段对照页面 |

原件访问可由单独受控路由提供；不将磁盘绝对路径直接当作浏览器链接。

### 5.3 输入和数据口径

- `direction` 固定为 AP；`source_type` 区分 upload/email。
- 邮件来源保留 provider、邮箱标识、provider_message_id、attachment_id/附件序号和原文件名；不要只依赖发件人或主题识别文件。
- 上传生成稳定的 source_upload_id；同一次请求重试复用该 ID。
- `receipt_id` 标识接收事件，`invoice_id` 标识业务发票；同一业务发票可能有多次接收事件。
- 保存文件哈希，但相同哈希不自动等于相同邮件投递。区分请求重试、重复接收与业务重复。
- 金额使用 Decimal 计算，接口可用十进制字符串；日期规范为 ISO 日期，缺失值保留 null；按币种分别处理。
- 原始提取结果与规范化字段分开保存；后续人工修订不可覆盖原始证据。
- processing_status、review_status 分开记录；结算、导出、通知不要复用一个总状态字段。

验收：相同接收键重试返回已有业务关联；新接收事件能关联旧发票并保留来源；不能因 HTTP 重试重复建票。

## 6. 第三步：真实保存与上传入口

2026-10-06 完成情况：后端已加入 Compose；派生工作流 `n8n_workflows/01_AP_intake_upload_v1.json` 已导入本地 n8n 并发布。文本/OCR PDF 上传、原件读回、相同来源重试、新来源同内容及来源冲突均已验证；重启后端后仍可读回。操作说明见 `step_03_upload_runbook.md`，结果见 `step_03_upload_verification.json`。当前仅完成接收，不代表第 4 步 OCR 已实现。

后端先完成：接收单个 PDF → 检查文件类型和大小 → 生成服务端文件名 → 持久化原件 → 登记来源和关联 → 返回 ID。

保留上传文件名作为元数据，不直接用它拼接任意磁盘路径。原件目录和数据库都需要持久化；不要仅写容器临时文件系统。保存或登记失败时返回明确失败，不返回伪成功 ID。

在派生 n8n 工作流中先配置上传入口（优先 Form Trigger，按目标实例可用参数配置）。统一到每个 item 只有一份待处理附件，并使用明确的 binary 属性，例如 data。保留来源元数据，HTTP Request 用 multipart 传文件。

Compose 后续增加后端时，n8n 容器通过服务名访问后端，例如 `http://backend:8000`；用户浏览器的审核 URL 使用用户可访问的地址，例如 `http://localhost:8000/review/...`。两者不可混用。端口和服务名均待实际配置。

验收：上传后原件可以打开，内容与输入一致；数据库有接收记录；重试不生成第二张业务发票。至此只能报告“保存登记已验证”。

## 7. 第四步：提取、校验与两层查重

### 7.1 提取

从保存的原件按页检查输入与文本质量；可靠文本层走原生解析，图片、空文本或质量不足的页面走 OCR，再进入共同结构化提取。第一轮同时验证两条路径；LangChain 仅在能简化该步骤时引入。第一阶段不引入 LangGraph。

提取字段至少覆盖供应商、发票号、开票日、到期日、币种、净额、税额、总额；根据样本增加行项目。缺失或不确定字段明确标记，不能让模型不断补行来凑齐金额。

OCR 适配层是本阶段必要实现，首轮已有 11 份无文本层 PDF。截图中的 Google Vision / AWS Textract 是候选，不是已经选择或接入的服务。未实现 OCR 时返回明确的待支持状态，不能将空文本当作提取成功，也不能把非空文本一律视为可靠文本。

### 7.2 校验

确定性代码检查必要字段、日期格式、币种、金额结构和净额/税额/总额关系。容差应根据币种精度及已选样本规则明确配置，不让模型决定。涉及折扣、运费和多税率时，先核对样本结构，不能用简单行合计错误判定所有发票。

业务异常保存为稳定的异常代码和可读原因，进入人工审核。服务超时、解析崩溃、数据库失败属于技术错误，不能创建看似完成提取的正常审核任务。

### 7.3 查重位置

1. 接收登记时检查来源接收键：避免重试重复建票和重复处理。
2. 提取后以可靠供应商标识和规范化发票号为基础检查业务重复，结合币种、金额等信息呈现候选。供应商名称相似不能单独证明重复。

确认为同一次处理重试时复用记录；疑似业务重复保留证据并标记审核，不静默删除新输入。缺少关键字段时记录“无法判定”，不伪装成已通过查重。

验收：正常样本字段与标准答案一致；异常可以解释；相同业务发票从新邮件再次到达能够被标记，同时保留新的接收来源。

## 8. 第五步：审核任务和最小页面

后端以 invoice_id 幂等创建待审核任务，返回 `direction=AP`、`review_status=pending` 和真实 review_url。同一发票重试不创建多个待审核任务。

页面至少显示原件、提取字段、校验异常及重复候选，并能通过 invoice_id 查到数据库内容。只读展示完成时，记录为“审核任务已创建、审核入口可查看”，不要声称批准/拒绝闭环完成。

本阶段停在待审核状态。后续实现修改、重校验、批准/拒绝和审计记录后，由后端提交审核完成事件给 02；01 的原执行已经结束。

验收：从浏览器打开返回链接，看到对应原件与字段；刷新页面仍能读到持久化记录，不依赖上一轮 n8n 执行内存。

## 9. 第六步：审核通知与单张 happy path

先配置本地测试收件端，例如 Mailpit。n8n 使用后端返回的 review_url 组装通知，包含 invoice_id、供应商/发票号、金额与币种、异常摘要和审核链接。

邮件发送成功和任务创建成功分开记录。通知失败只重试通知，不重建发票或任务。第一版记录失败即可，复杂补偿后置；SMTP 超时后的投递结果可能不确定，不能保证仅靠重试绝无重复通知。

Mailpit 适合接收通知和查看邮件内容；它不替代模板中的 Gmail API 入口。参考：[SMTP/HTTP 接收](https://mailpit.axllent.org/docs/usage/sending-messages/)。

验收：测试收件端实际收到通知，点击链接能打开正确发票。仅生成邮件正文或假 URL 不算完成。

## 10. 第七步：从模板接入邮件

派生文件建议命名 `n8n_workflows/01_AP_intake_v1.json`；未接后端的试接版本名称包含 mock。保持 inactive，完成目标实例检查后再决定启用。

### 10.1 节点改造清单

| 原节点 | 处理方式 |
| --- | --- |
| Schedule Trigger / Get many messages | 复用邮件轮询思路，修改测试邮箱筛选；开始用手动执行 |
| Gmail-Get_Invoice | 根据实际返回结构决定是否保留，避免重复下载附件 |
| Filter-contains_attachment | 改为逐附件类型检查；原条件不证明是 PDF |

| Delete a file1 / Delete a message | 从派生版本移除 |
| Sticky Notes | 重写英语说明，注明原模板来源、改动、待接入和实际验证层级 |

### 10.2 最终连接顺序

邮件获取或上传 → 拆附件 → 统一来源字段 → 保存登记 → 重复投递分支 → 提取/校验/业务查重 → 结果分流 → 创建审核任务 → 通知 → 结束。

不要机械照搬原模板“上传 Drive 再下载”的顺序。多附件邮件必须每附件一个 item，并保持来源关联；不将多页 PDF 拆成多张业务发票。

原模板只查最近一小时，停机超过窗口可能漏信。初期使用可控测试批次；稳定后选择可重扫范围并依靠后端幂等。不要用删除邮件来代替成功登记。

验收：单封带 PDF 的邮件进入同一后端；一封含两份 PDF 时得到两个正确关联的处理项；无附件/非 PDF 不进入提取。

## 11. 第八步：邮件生成和批量测试

后续独立编写测试脚本，读取样本清单，使用 MIME 邮件附加 PDF，通过专用测试账号的受支持发送方式投递。一个发件账号和一个收件账号即可，不必模拟几十个真实发件账号。

每封使用可追踪主题，例如 `[AP-DEMO][batch-001][case-003]`；记录 case_id、批次、附件、发送结果和邮箱提供商返回标识。SMTP Message-ID 与 Gmail 的 provider message ID 是不同标识，不能混为一谈。

三种重复场景分别测：同一收信结果再次处理；同一个 PDF 放进新邮件；不同文件包含同一张业务发票。只有第一种直接属于相同邮件接收的重跑。

测试顺序：1～2 封连通性 → 5～10 封端到端 → 10～20 个代表性场景 → 100～500 个可控批量输入。批量投递速度按邮箱实际限制设置，不默认无限发送；邮件投递吞吐与后端文档处理吞吐分开测。

第一批正常链路完成后，集中补以下场景：多附件、无附件、扫描 PDF、多页、缺字段、金额异常、重复接收、业务重复、模型/后端故障、通知失败和重启恢复。审批修改与拒绝测试在审核写入功能实现后执行。

验收以清单核对：发出的有效附件数、接收记录数、唯一业务发票数、待审核任务数、失败数及通知数能够解释；不只看 n8n 执行是否绿色。

## 12. Mock 与待接入规则

- 待接入：接口尚不存在或不可访问；节点说明写明依赖，不返回假成功。
- Mock：测试节点明确标记 `MOCK`，返回 `is_mock=true`；固定样例提取结果只用于测试分流。
- 真实保存 + Mock 提取：仅报告保存已验证、提取为模拟。
- Mock review_url：不能声称可审核，也不能计入最终 happy path 验收。
- 不把 Mock 数据混入真实记录；使用隔离测试数据库或可识别的测试批次，并保留模拟标记。
- 第一阶段最终验收使用真实样本、真实持久化、真实提取、真实审核入口和实际到达测试收件端的通知。
